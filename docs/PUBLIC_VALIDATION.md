# Public compatibility validation

CafeOS Analyzer needs evidence from real POS export shapes, but public GitHub must not become a storage location for merchant data.

## Public-safe evidence

You may share:

- POS/source name and export report name
- file format and sheet names
- column/header names
- row counts and date-range metadata
- store-count bucket
- schema-only compatibility profile generated by `validation:profile`
- mapping failures or parser errors that do not include transaction-row values

Generate a schema-only profile locally:

```bash
npm install
npm run validation:profile -- path/to/export.xlsx > compatibility-profile.json
```

Review the JSON before posting it publicly.

## Keep local/private

Never post to a public issue, pull request, commit, gist or discussion:

- raw CSV/XLSX merchant exports
- customer names, phone numbers or emails
- transaction rows or transaction IDs
- real store/product names when they identify a merchant
- credentials, API keys, HMAC keys or tokens
- willingness-to-pay notes, contact details or private operator interviews
- field-validation registries

For row-level reproduction, use the local pseudonymized validation-pack workflow described in `docs/FIELD_VALIDATION_PROTOCOL.md`.

## Evidence order

1. Prove the export can be parsed and mapped.
2. Reconcile deterministic net sales and order count against the source report.
3. Only then evaluate higher-level insights.
4. Product-market-fit claims still require the locked 10-20 target-ICP field-validation process.

Public compatibility reports improve import coverage. They do not count as willingness-to-pay or repeat-use evidence by themselves.
