# Database model

## Authority

- `db/migrations/001_analyzer_core.sql` — existing Analyzer persistence contract.
- `db/contracts/control_tower_core.sql` — **Control Tower schema contract under CI**, not yet a Supabase migration.
- `docs/CONTROL_TOWER_IMPLEMENTATION_SLICE.md` — thin-slice product boundary.

The Control Tower contract must be promoted into a migration using the Supabase CLI migration workflow after it passes local/staging database validation. Do not invent a migration filename by hand.

## Analyzer core

### Idempotency

Each normalized line receives a deterministic `source_record_key`. The database enforces `unique (tenant_id, source_namespace, source_record_key)`, so overlapping exports do not double-count previously committed lines.

An entire normalized import also receives a deterministic fingerprint and is unique within `(tenant_id, source_namespace)`.

### Tenancy

Every mutable business row carries `tenant_id`. Existing Analyzer tables use RLS and `private.has_tenant_access(...)`.

## Control Tower schema contract

### Stable business graph

`stores`

- stable tenant/source identity: `(tenant_id, source_namespace, external_key)`
- no immediate removal of raw source store text from line items
- line items gain nullable `store_id` for deterministic promotion

`customers` + `customer_identifiers`

- customer identity is tenant-local
- identifiers are deterministic only
- matching values are HMACs, not fuzzy person matches
- identifier rows are server-owned in the first slice
- line items gain nullable `customer_id` as a migration bridge

Composite foreign keys use `(tenant_id, id)` so an application bug cannot reference another tenant's Store, Customer, Attention or Action object.

### Attention → Action → Measurement

`attention_items`

- deterministic `attention_key` prevents duplicate workflow objects for the same evidence
- stores metric/scope/current/baseline/delta/coverage/evidence/detector version
- authenticated users can read but do not write trusted numeric insight objects

`actions`

- bounded action types only: investigate, follow-up, segment, experiment hypothesis
- owner/admin/analyst may create/update
- viewer remains read-only
- resolution/dismissal requires a note and resolved timestamp

`action_status_history`

- status history is written by a database trigger
- users read audit history but do not directly write it

`measurement_windows`

- before/after windows are explicit
- client-created windows start `pending` with no trusted values
- `delta_value` is generated by Postgres from measured minus baseline value
- authenticated clients cannot update measured values

This supports measured change without implying causal attribution.

## Supabase 2026 grants + RLS model

Current Supabase guidance treats **grants and RLS as separate controls**. New projects may not auto-grant Data API privileges for tables in `public`.

Therefore the Control Tower contract:

1. explicitly revokes anonymous access;
2. explicitly grants only required table operations to `authenticated`;
3. enables RLS on every new `public` table;
4. keeps sensitive matching identifiers and trusted metric writes server-owned;
5. grants `service_role` explicit table privileges for server-side work;
6. grants `USAGE` on the `private` schema while keeping helper-function execution restricted.

References:

- https://supabase.com/docs/guides/database/postgres/row-level-security
- https://supabase.com/docs/guides/api/securing-your-api
- https://supabase.com/changelog/45329-breaking-change-tables-not-exposed-to-data-and-graphql-api-automatically

## Promotion workflow

Before a real migration exists:

1. use an environment with the Supabase CLI available;
2. inspect current CLI syntax with `supabase --help` and `supabase migration new --help`;
3. create the migration with `supabase migration new control_tower_core`;
4. copy/reconcile the reviewed contract into the generated migration file;
5. apply only to a local/disposable/staging database first;
6. run DB/RLS tests with the current CLI-supported test workflow;
7. run Supabase security and performance advisors;
8. reconcile any generated diff/migration history;
9. only then consider a production migration.

No real merchant data may enter Control Tower persistence before tenant-isolation and migration tests pass.

## Deferred

The Control Tower core intentionally does **not** add:

- campaign delivery
- loyalty balances
- payment
- inventory
- accounting/payroll
- generic task/project management
- experiment/exposure/conversion tables

Those remain later evidence-gated modules.
